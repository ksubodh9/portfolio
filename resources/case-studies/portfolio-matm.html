Project Overview

What was built

A complete Micro ATM banking feature — from scratch — integrated with the IServeU third-party SDK, enabling agents on the MaddoxPay platform to perform card-based cash withdrawals and balance enquiries at customer doorsteps using a biometric fingerprint reader.

💳

Cash Withdrawal

Agents can initiate amounts from ₹100–₹10,000 in configurable multiples. A dedicated popup SDK window handles biometric capture and card interaction, keeping the main application state clean.

📈

Balance Enquiry

Real-time account balance lookup via biometric authentication — no amount required. Commission-free by design, handled cleanly with a dedicated code path in the commission engine.

📱

Device Registration Portal

Agents register their MATM hardware device serial numbers before transacting. Full lifecycle: pending → approved / rejected → superseded, with admin review and re-submission support.

⚙️

Commission Engine

A slab-based, amount-ranged commission calculator that automatically detects the agent's hierarchy tier — Agent, Distributor (RM), or Super Distributor (SM) — and routes the right earnings to each level.

📋

Transaction Dashboard

A rich analytics view with nested Highcharts pie charts for CW/BE breakdowns by status, a 7-day bar chart for daily activity, summary stats, and an interactive transaction history table with instant repeat-transaction.

📄

Digital Receipts

Every completed transaction generates a printable, branded receipt page, accessible via encrypted URL. Automatically opened after the SDK callback fires, with a one-time localStorage token bridge.

System Design

A layered, event-driven architecture — the browser launches an isolated SDK popup, the Laravel backend orchestrates wallet and commission logic, and a webhook callback from IServeU closes the transaction loop.

Code Architecture

Layer-by-layer breakdown

1

HTTP Controllers

Two focused controllers handle the web surface — IsuMatmTransactionController for initiating, tracking and receiving callbacks, and IsuMatmDeviceRegistrationController for the full device lifecycle. Both are injected with service and repository interfaces.

Service Layer

The core business logic lives in two dedicated services: MatmService builds encrypted SDK payloads, handles credential validation, normalises multi-variant callback field names across SDK versions, and resolves the mobile number. MatmCommissionService detects the user's distribution hierarchy and applies the correct slab model.

Repository Pattern

All database interactions are abstracted behind interfaces — IsuMatmTransactionRepositoryInterface and IsuMatmDeviceRegistrationRepositoryInterface — keeping controllers lean and enabling easy testing.

4

Middleware & Route Guards

The custom is.matm.device.registered middleware gates all transaction routes — automatically redirecting unapproved or pending agents to the relevant status page. IsServiceSubscribed middleware ensures the agent has an active service subscription.

Database Design

Two new migration-managed tables: isu_matm_transactions captures the full transaction audit trail including raw request/response/callback payloads, and isu_matm_device_registrations tracks device state, serial uniqueness, approval timestamps, and rejection reasons.

A setInterval poller detects when the popup closes and triggers a page reload.

Engineering Decisions

Challenges & how they were solved

⚠️ Challenges Faced

  • IServeU SDK callback uses inconsistent field names across SDK versions (e.g., clientRefID vs clientRef_Id vs clientRefId)
  • Callback arrives from IServeU without auth headers — standard credential checks would block it
  • SDK must open in a separate popup — the payload can't be embedded in a URL (too long + insecure)
  • Wallet debit for CW must be atomic — race conditions could cause double-debit
  • Commission calculation must handle 3 different user tiers with different slab tables
  • Device serial numbers must be globally unique across all users

✅ Solutions Implemented

  • Built a normalizeCallbackPayload() method that gracefully resolves all known field name variants in priority order
  • Designed hasValidCallbackCredentials() to allow empty-header callbacks through, falling back to DB-side clientRefId matching for authenticity
  • Used a one-time localStorage token bridge — payload stored briefly and removed immediately after reading, isolating data between sessions
  • Wrapped wallet credit inside a DB transaction with custom exception types for insufficient balance, invalid ops, and negative balances
  • Modelled a hierarchy detector that selects the right Eloquent model at runtime: MasterIsuMatm*Commission
  • Added a global uniqueness check on serial numbers before processing any registration attempt

Commission Engine Hierarchy-aware, slab-based calculation with SHA-256 audit checksum
MatmCommissionService.php 
public function calculate(int $serviceId, $user, string $transType, float $amount = 0): ?array
{
    // Balance Enquiry earns no commission — short-circuit immediately
    if ($transType === 'matm_be_transaction') {
        return $this->balanceEnquiryResponse();
    }

    // Detect agent's position in the distribution chain
    [$hasSM, $hasRM] = $this->detectHierarchy($user);

    // Dynamically resolve the correct Eloquent slab model
    $model = $this->resolveCommissionModel($hasSM, $hasRM);

    $slab = $model::where('min_range', '<=', $amount)
        ->where('max_range', '>=', $amount)
        ->first();

    // Build response + log with integrity checksum for audit trail
    $response = $this->buildCommissionResponse($slab, $amount, $hasSM, $hasRM, $transType);

    Log::channel('isu-matm-audit')->info('[MatmCommission] Commission calculated', [
        'output'         => $response,
        'input_checksum' => hash('sha256', json_encode($inputData)),
        'execution_ms'   => round((microtime(true) - $start) * 1000, 2),
    ]);

    return $response;
}

Frontend SDK Bridge One-time localStorage token securely passes payload to popup window
transaction.blade.php — launchMatm() 
// Open popup immediately on user gesture (before async delay — avoids browser popup block)
sdkWindow = window.open('about:blank', '_blank');

// After API responds with encrypted SDK payload, store it under a unique token
fetch("{{ route('user.isu-matm.initiate') }}", { method: 'POST', body: formData })
  .then(res => res.json())
  .then(response => {
    // One-time token ensures payload can't be replayed
    const token = 'matm_' + Date.now() + '_' + Math.random().toString(36).substr(2, 8);
    localStorage.setItem('matmSdkPayload_' + token, JSON.stringify(response.data));
    sdkWindow.location.href = sdkUrl + '?token=' + encodeURIComponent(token);

    // Poll for popup close → reload to show updated transaction state
    pollTimer = setInterval(() => {
      if (sdkWindow.closed) { clearInterval(pollTimer); window.location.reload(); }
    }, 1000);
  });

Security

Built secure by default

Security wasn't bolted on — it was part of every architectural decision, from credential handling to callback validation.

🔐

AES Header Encryption

Every SDK request header is encrypted with a time-bound epoch nonce using AES via the shared EncDecService — credentials never travel in plain text.

⛳

Constant-Time Comparison

Credential validation uses hash_equals() throughout — immune to timing-based side-channel attacks on string comparison.

📋

Encrypted Receipt URLs

Transaction IDs in receipt URLs are wrapped with Laravel's Crypt::encryptString() — sequential IDs are never exposed to the client.

🚪

One-Time SDK Token

The localStorage bridge token is removed immediately after first read — the SDK payload cannot be replayed even if the storage key is somehow observed.

🔒

Input Sanitisation

All inputs are validated server-side with strict rules: digits:10 for mobile, alpha_num for serial numbers, and in:... for enum fields.

👤

Mobile Number Masking

Transaction history always displays only the last 4 digits of the customer mobile number — personally identifiable data is protected in the UI.

📄

Full Audit Logging

Every stage — payload build, wallet creation, commission calculation, and callback receipt — writes to a dedicated isu-matm-audit log channel with SHA-256 input checksums.

⚡

Atomic Wallet Operations

Wallet debits run inside a database transaction with typed exception handling for insufficient balance, negative balance, and invalid operation — no partial states.

Development Journey

How the feature was shipped

Phase 1

API research & database design

Studied the IServeU MATM SDK documentation, mapped out all callback field variants, and designed the two database tables with full audit-trail columns. Established the repository interfaces before writing any concrete code.

Phase 2

Service layer & encryption

Built MatmService to handle credential loading, AES-encrypted header construction, SDK payload assembly, callback credential validation, payload unwrapping, and field normalisation across SDK versions.

Phase 3

Commission engine

Implemented the multi-tier commission calculator with automatic hierarchy detection, three separate Eloquent slab models, a SHA-256 audit checksum on every calculation, and a fast-path short-circuit for Balance Enquiry.

Phase 4

Controllers, middleware & routing

Wired up both controllers with dependency injection, applied IsMatmDeviceRegistered and IsServiceSubscribed middleware, and defined all web + API routes including the unauthenticated webhook endpoint.

Phase 5

Frontend & SDK popup bridge

Designed the single-page transaction dashboard, built the localStorage token bridge for the SDK popup, integrated Highcharts for nested pie and 7-day bar charts, and added the repeat-transaction feature from the history table.

Phase 6

Device registration portal & user manual

Built the full device registration flow with all lifecycle states (pending / approved / rejected / superseded), a dedicated pending status page, and a rich HTML user manual covering every step of the service.
