Wallet Engine

Dual wallet system — purpose-built per service type

A core architectural decision — two separate wallet systems with different balance types, different exception models, and different commission flows. Each wallet wraps every operation in a database transaction for atomicity.

◕ Main / Debit Wallet

  • Primary agent balance — funded via payment gateway top-ups and manual admin credits
  • Used for: Cash Deposit, domestic money transfers, document applications, bill payments, recharge, toll tags, travel bookings, tax filing
  • Custom exception hierarchy for insufficient balance and negative balance edge cases
  • Balance validation gate executed before every debit operation
  • Every debit creates both a main transaction record and a commission distribution record atomically
  • Government kiosk portal users are restricted from topping up — they operate exclusively on the credit wallet
  • Admin can manually credit or debit agent wallets from the dashboard
🛠️ Architecture: Single service class entry point — ProcessDebitTransaction() — used by all debit-wallet services to guarantee consistent balance handling

◕ Credit Wallet

  • Commission credit balance — automatically populated from commission distributions on successful transactions
  • Used for: AEPS Cash Withdrawal, AEPS Mini Statement, AEPS Balance Enquiry, Micro ATM withdrawal
  • Government kiosk portal operators use credit wallet exclusively
  • Balance tracked in a dedicated ledger table with a running balance column per record
  • A configurable flag controls whether balance is physically transferred or only recorded (for settlement-style flows)
  • Custom exceptions for insufficient balance and invalid wallet operation scenarios
  • Balance readable at any point via a dedicated repository query
🛠️ Architecture: Single service class entry point — ProcessCreditTransaction() — handles commission distribution inline with multiple injected repositories for atomicity
CommissionDistributionService — pseudocode: hierarchy-aware commission distribution with payment plan override
// After a successful wallet transaction, calculate and persist commission splits
// across all hierarchy tiers. Custom payment plan rates override slab defaults
// when the agent is enrolled in one.

FUNCTION DistributeCommission(orderDetails, walletTransaction, currentUser):

    commissionRecord = CommissionDistributionRepository.Create({
        wallet_type:       transactionDirection,
        transaction_id:    walletTransaction.id,
        total_amount:      orderDetails.amount,
        total_commission:  orderDetails.commissionData.totalAmount,
        payable_amount:    orderDetails.totalPayable,

        // Platform tier
        platform_comm_%:   orderDetails.commissionData.platformPercent,
        platform_comm_$:   orderDetails.commissionData.platformAmount,

        // Tier-2 distributor (Super Manager)
        tier2_comm_%:      orderDetails.commissionData.tier2Percent,
        tier2_comm_$:      orderDetails.commissionData.tier2Amount,

        // Tier-1 distributor (Regional Manager)
        tier1_comm_%:      orderDetails.commissionData.tier1Percent,
        tier1_comm_$:      orderDetails.commissionData.tier1Amount,

        // Agent
        agent_comm_%:      orderDetails.commissionData.agentPercent,
        agent_comm_$:      orderDetails.commissionData.agentAmount,
    })

    // If agent is enrolled in a custom payment plan,
    // record plan usage alongside the commission record.
    activePlan = PaymentPlanRepository.GetActivePlan(currentUser.id)
    IF activePlan EXISTS:
        PaymentPlanTransactionRepository.RecordUsage(activePlan, walletTransaction)
Commission Architecture

3-tier hierarchical commission distribution

Every transaction — regardless of service — flows through the same commission distribution model. The hierarchy is Agent → Regional Manager → Super Manager → Platform. Slabs are configurable per service per tier from the admin panel.

📈 Commission Hierarchy

PLT
Platform

Platform margin after all distributions — configurable as percentage or flat amount per service

SM
Super Manager (Tier-2)

Top distributor in agent chain — earns override commission on every transaction below

RM
Regional Manager (Tier-1)

Mid-level distributor — configurable commission on agent transactions

AG
Agent

Transaction-initiating user — earns base commission on every successful transaction

🔮 How Commission is Calculated

  • Service + transaction type → slab lookup by amount range matching the transaction value
  • Agent hierarchy traversed to determine which tiers (SM/RM) are present in the chain
  • Correct commission model selected based on hierarchy depth: Super Distributor → Distributor → Base
  • All percentage and amount splits stored in a per-transaction commission distribution record
  • Biometric transaction commissions include SHA256 input + output + combined checksums per calculation for tamper-evident auditing
  • Government kiosk portal users: dedicated commission override path with service-specific rates
  • Custom payment plan: if agent is enrolled in a plan, plan-tier rates override standard slabs

⚙️ Admin Commission Controls

  • Commission configuration panel — set base slabs per service per transaction type
  • Distributor override: Regional Manager can set custom agent-level rates
  • Super Manager can adjust commission across the distributor sub-tree
  • Commission logs visible in MIS with per-transaction breakdown
  • Service-specific rules applied per transaction type (e.g., zero commission on balance enquiry)

📄 Commission Data Models

  • Base slab configuration — per service, per transaction type
  • Biometric banking base slabs — dedicated model
  • Regional Manager (Tier-1) slab overrides
  • Super Manager + Regional Manager (Tier-2) slab configuration
  • Per-transaction commission distribution record (all splits stored)
  • Custom payment plan configuration model
  • Payment plan usage tracking model

🔎 User Hierarchy Resolution

  • Dedicated trait resolves the full Agent → RM → SM chain for any given user
  • Redis-cached per user and chain — invalidated on user tree changes
  • Prevents redundant database traversal on every transaction request
  • Admin can impersonate any chain node for reporting and auditing

Government Portal Integration

eMitra — Rajasthan Government Kiosk Portal

MaddoxPay is integrated as a licensed service provider within the Rajasthan Government's official eMitra kiosk portal — allowing eMitra kiosk operators to access AEPS biometric banking services directly from the government platform.

🔐 AES-Encrypted SSO Redirect

  • Government portal redirects with an AES-CBC encrypted payload
  • Decrypted server-side — no plaintext credentials transmitted via URL or query string
  • SSO token verified against the government's SSO endpoint before any session is established
  • Kiosk operator details fetched and stored in a short-lived session

⚟️ Circuit Breakers on Government APIs

  • Dedicated circuit breakers on government B2B transaction and verification endpoints
  • Prevents transaction flows from blocking when the government API is slow or unavailable
  • Error categorizer classifies failure types: timeout, authentication failure, server error
  • Circuit opens after a configurable failure threshold; auto-resets after cool-down window

📋 Integrity Checksums & Request Signing

  • Government B2B and verification requests include MD5 checksums over credential arrays
  • Consumer keys generated with cryptographic randomness for request uniqueness
  • Timestamps with millisecond precision to prevent replay attacks
  • Full request and response audit log per government API call

🔄 Reconciliation Job

  • Background queue job for batch reconciliation of eMitra transactions
  • Verification service compares MaddoxPay-side status against eMitra-side status for pending/failed records
  • Force-cancel workflow with optional eMitra API bypass for irrecoverable states
  • Full eMitra MIS report with date-range DataTables

👥 Dual User Mode from One Controller

  • A single boolean flag on the user record branches all wallet, commission, and API logic throughout the request lifecycle
  • Session guard: transaction type restricted to the active eMitra service mapping at runtime
  • eMitra service ID re-resolved dynamically when offered under alternate session context
  • Graceful fallback: base service cloned with eMitra service ID override when no specific record exists

🗂 Data Architecture

  • Per-transaction eMitra settlement record — linked via polymorphic relation
  • Incoming eMitra redirect session records for audit trail
  • Service ID mapping table — maps eMitra service IDs to MaddoxPay service IDs
  • Polymorphic association between wallet transaction and eMitra-specific record
System Architecture

How the entire platform is structured

A layered, repository-driven architecture — every service behind an interface, business logic in dedicated service classes, no database calls from controllers.

1

Route Layer — Web + API

Separate route files per concern: agent service routes, webhook API routes, and auth/dashboard routes. Middleware groups enforce authentication, service subscription, and account status. CSRF-exempt webhook routes are validated by provider-specific signature checks instead.

ServiceRoutes (web) WebhookRoutes (api) AuthMiddleware ServiceSubscriptionMiddleware
2

Controller Layer — Thin, Dependency-Injected

Controllers are dependency-injected via constructor. No Eloquent queries inside controllers — all data access delegated to repositories. Controllers orchestrate: validate request → call service → commit or rollback → return view/JSON. The most complex controller (AEPS biometric banking) has 20+ injected dependencies covering gateways, wallet services, commission services, repositories, and notification services.

BaseController (injectable) ServiceBaseController Route middleware groups Form Request validation
3

Service Layer — Business Logic & Third-Party Clients

All business logic lives in dedicated service classes. Gateway clients encapsulate all HTTP communication, authentication, and response parsing for each external provider. Wallet services are the sole entry points for wallet operations. Commission services apply slab resolution and hierarchy detection.

BiometricBankingService GovernmentPortalApiService DebitWalletService CreditWalletService GovPortalTransactionService CommissionCalculationService PayoutGatewayService RechargeAggregatorService
4

Repository Layer — All DB Access Behind Interfaces

Every model access is behind a repository interface registered in the service container. Repositories are injected into controllers and services — enabling easy swapping of implementations and clean unit-testability. Includes repositories for wallets, transactions, commission distributions, users, services, DMT remitters/beneficiaries, biometric records, government portal services, and more (30+ total).

WalletRepositoryInterface TransactionRepositoryInterface CreditWalletTransactionRepository CommissionDistributionRepository BiometricTransactionRepository GovPortalServiceRepository PayoutTransactionRepository UserRepositoryInterface
5

Database Layer — Relational + Extensible Schema

MySQL with a central transactions ledger table and a transaction metadata table — service-specific transaction details stored in dedicated tables per service type (biometric banking, domestic money transfer, micro ATM, government portal, document applications, etc.). The transaction model exposes typed relations to each service-specific table for unified querying in MIS reports.

transactions (central ledger) transaction_metadata credit_wallet_ledger commission_distributions biometric_transactions gov_portal_transactions payout_transfers document_applications
6

Queue + Jobs + Cache

Background jobs handle export generation, government portal reconciliation, and notification delivery. Redis caches user hierarchy chains (per user + chain combination, invalidated on user tree changes via a version bump mechanism). Activity logging captures all third-party API request/response pairs for audit and debugging.

GenerateExportJob ReconcileGovPortalTransactionsJob Redis (hierarchy cache) ApiActivityLogService HierarchyVersionBump()

Security

Security-first at every layer

🔐

AES-CBC Encryption

Government portal redirect payloads encrypted with AES-CBC. Decrypted server-side — no plaintext credentials in URL or transit.

📋

SSO Token Verification

Every government portal session validates the SSO token against the government's endpoint before any session is established.

👆

Biometric PID Pipeline

RD device returns encrypted XML PID block. Decrypted and parsed server-side — raw biometric data never stored or logged.

🔑

Server-Side Session Guards

Government portal transaction types restricted server-side by active service mapping — frontend bypass via direct POST returns 403.

🗂

Atomic Wallet Operations

All wallet debits/credits inside a database transaction — balance check, wallet record, commission record all-or-nothing.

🔄

SHA256 Commission Audit

Input + output + combined SHA256 checksum on every commission calculation — tamper-evident audit log per transaction.

⚡

MD5 Request Checksums

Government B2B and verification requests include MD5 checksums over credential payloads — payload tampering invalidates checksum.

⚟️

Circuit Breakers

Dedicated circuit breakers on government API endpoints. Opens on repeated failures — prevents transaction flows from hanging on API timeout.

📍

Geolocation Validation

Biometric 2FA locks agent coordinates. Haversine distance check on every transaction flags impossible location jumps.

🔓

Role-Based Access Control

All admin/manager/user routes gated via Cartalyst Sentinel. Each role has distinct permission sets enforced at route and controller level.

🛠️

JWT / Token Auth (APIs)

Alternate DMT gateway uses JWT authentication on every request. API tokens rotated per session. Mobile app API uses JWT guard.

👤

MPIN Verification

Sensitive operations require MPIN confirmation from the agent. PIN stored hashed — never verified in plaintext.

Designed and built the core architecture: role-based authentication with Cartalyst Sentinel, the dual wallet engine (Debit + Credit wallet services) with atomic database transactions and a custom exception hierarchy, the repository pattern across all models (30+ interfaces registered in the service container), and the 3-tier commission distribution model. Every subsequent service builds on these foundations.

Phase 2

First financial services — Recharge, BBPS, Document Applications, DMT

Integrated a mobile and DTH recharge aggregator, dual-gateway BBPS bill payment, national document authority application booking with document upload and negative registry check, and an alternate DMT gateway with JWT auth and AES payload encryption. Established the commission engine patterns used by all subsequent services. Built the first DataTables MIS reports and Excel exports.

Phase 3

MATM (Micro ATM) — Biometric integration

Built the full Micro ATM integration: multi-phase onboarding with live status polling, biometric XML PID decryption pipeline, daily two-factor authentication, cash withdrawal with credit wallet, 3-tier commission distribution, alternate banking partner referral fallback path with registration fee split, and WhatsApp receipt notifications.

Phase 4

DMT (Standard) — IMPS-based transfer channel

Built the standard domestic money transfer integration: remitter registration with Aadhaar OTP verification, configurable per-remitter limit enforcement, beneficiary management with bank account verification, IMPS transfer with debit wallet deduction, multi-status transaction lifecycle (pending → processing → success/failed/reversed), transaction reversal with wallet refund, and full DataTables MIS.

Phase 5

AEPS biometric banking — the most complex feature

The platform's most architecturally demanding module: biometric banking with multi-phase KYC onboarding, Bio-KYC, bank eKYC, daily biometric two-factor authentication, four transaction types with dual wallet routing, three-tier commission engine with SHA256 tamper-evident audit trail, centralized response handling, haversine geo-validation, and three-way reconciliation. This service runs the highest production volume on the platform.

Phase 6

eMitra government portal — the most innovative integration

Integrated MaddoxPay as a licensed service provider within the Rajasthan Government's eMitra portal: AES-encrypted redirect payload decryption, SSO token verification against the eMitra SSO endpoint, dual user mode from a single controller (a boolean flag branches all wallet, commission, and API logic for eMitra operators), eMitra B2B transaction with MD5 checksums and circuit breakers, eMitra service ID re-resolution edge case handling, batch reconciliation job, and full eMitra MIS.

Phase 7

Payout, additional services, admin suite maturity

Service Engineering Spotlights

The three most architecturally demanding services

AEPS, MATM, and DMT sit at the hardest intersection of real-money transactions, biometric hardware, and government infrastructure. Here's the engineering behind each.

👆
AEPS — Aadhaar Enabled Payment System

Biometric Banking + eMitra Government Portal

Most Complex 20+ Dependencies

The Engineering Challenge

AEPS is the hardest service on the platform: biometric hardware (Morpho/Mantra RD devices) outputs an encrypted XML PID block that must be decrypted server-side, the transaction must hit a live UIDAI-compliant gateway, the result must atomically update two wallets and distribute commission across three tiers — all while the government eMitra portal creates a second execution path that reuses the same controller with completely different wallet, commission, and API logic. A single boolean flag on the user record branches the entire request lifecycle.

Key Engineering Decisions

  • Multi-phase KYC onboarding: biometric registration, Bio-KYC, and bank eKYC as distinct sequential stages, each with its own status tracking
  • Daily biometric two-factor authentication — coordinates captured and locked; Haversine distance check flags impossible location jumps on every transaction
  • Centralized response handler normalises success, failure, timeout, and partial states across providers into a uniform transaction lifecycle
  • SHA-256 input + output + combined checksum on every commission calculation — tamper-evident audit per transaction
  • Three-way reconciliation job: MaddoxPay status vs. gateway status vs. eMitra status — force-cancel workflow for irrecoverable states
  • Circuit breakers on all government API endpoints — configurable failure threshold, auto-reset after cool-down

MATM — Micro ATM

Biometric Cash Withdrawal via Hardware SDK

SDK Integration Polling Lifecycle

The Engineering Challenge

MATM adds a hardware layer that AEPS doesn't have: a third-party SDK served as a browser popup bridges the physical Micro ATM device to the web platform. The SDK fires a JavaScript callback with a transaction result payload whose field names changed between SDK versions — requiring a normaliser layer to handle both. The onboarding flow requires live polling of provider-side registration status across multiple stages (device registration, biometric registration, bank eKYC) before any transaction can be attempted.

Key Engineering Decisions

  • AES-encrypted bridge between the SDK popup and the main window — prevents payload tampering during the cross-window callback
  • Callback field normaliser abstracts SDK v1 and v2 response schemas into a single internal format — the rest of the service is SDK-version-agnostic
  • Multi-stage onboarding with server-side polling: each stage (device reg → biometric reg → bank eKYC) polls the provider API on a timer until confirmed or timed out
  • Alternate banking partner referral fallback: when primary onboarding fails, an alternate partner registration flow triggers with a separate registration fee split logic
  • Daily biometric 2FA with the same coordinate-locking and Haversine validation as AEPS
  • Commission distribution feeds into the same 3-tier SHA-256 audit trail used across all biometric services

DMT — Domestic Money Transfer

IMPS Transfers + Alternate Gateway with AES Auth

Dual Gateway Idempotency

The Engineering Challenge

DMT runs two completely separate gateway integrations in parallel — the standard IMPS gateway and an alternate gateway with a different authentication model (JWT + AES-encrypted payload headers reconstructed per-request from a time-bound seed). Both share the same remitter and beneficiary data model but diverge in their transfer lifecycle, webhook shapes, and refund flows. The registration fee — charged once per remitter — must be idempotency-guarded against double charges even under concurrent requests.

Key Engineering Decisions

  • OTP-verified remitter onboarding with Aadhaar-based identity check — configurable per-remitter monthly transfer limit enforced at service layer, not DB constraint
  • Penny-drop bank account verification before any beneficiary is confirmed — failed verifications are recorded but do not block future retry
  • Alternate gateway: JWT auth token + AES payload header reconstructed from a time-bound seed on every request — the seed validity window is narrower than typical HTTP timeout, requiring a pre-request freshness check
  • Idempotency guard on registration fee: pessimistic lock on the remitter record during fee deduction prevents double-charge on concurrent requests
  • Pessimistic locking on webhook handler — duplicate provider callbacks on the same transfer attempt are detected and discarded without state mutation
  • Transaction reversal: failed IMPS triggers a wallet refund via the same atomic service used for original debit, with a separate refund audit record
