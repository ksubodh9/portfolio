The Problem

Operational questions shouldn't require an engineer — or a live SQL console.

Operating a production Laravel app means constantly answering the same questions: "how many orders failed yesterday?", "why are users seeing 500s?", "what's our refund policy?" Normally that needs someone to write SQL, grep logs, or dig through docs. Handing that power to non-engineers is risky — raw database and log access are dangerous and hard to govern. LaraOpsCopilot makes those questions self-serve without giving anyone a live SQL console: every query is generated, guarded, proven read-only, approved, and audited, and every capability is scoped to the user's role.

The Intelligence

Three AI agents, one grounded Application Map

A Discovery Engine probes the host app's schema, user model, roles, and log channels to build a versioned Application Map. That map grounds every agent, so the same code works against any Laravel schema without hard-coded table or column names.

📊
NL → SQL

Database Intelligence

Translates natural language into a parameterized, read-only SELECT grounded in the Application Map. A dual SQL guard validates the query on both the Python and PHP sides; a human approval flow gates execution; and queries run on a dedicated read-only connection with a row cap and statement timeout.

Log RCA

Log Intelligence

Ingests and PII-masks logs before storage, normalizes and clusters errors by signature, then generates deterministic heuristics plus LLM root-cause narratives. "Show top exceptions today" and "why are users seeing 500 errors?" return clustered, explained results instead of a wall of stack traces.

Knowledge Base

Upload → sliding-window chunk → embed → FAISS index → semantic search → grounded answer with citations. Native txt / md / docx / pdf extraction. "What's our refund policy?" returns a cited answer drawn from an uploaded SOP — no hallucinated facts.

Architecture

A polyglot monorepo split across a contract boundary

A Composer package installs into the host Laravel app; a separate FastAPI service serves the AI. The two agree on every request and response shape through a single OpenAPI contract, validated in CI.

monorepo/
# Polyglot monorepo split across a contract boundary
packages/core/     # laraopscopilot/core — Composer package (PHP 8.2+)
services/ai/       # FastAPI AI backend — RAG, NL→SQL, log RCA (Python 3.11+)
contracts/         # OpenAPI spec — single source of truth for package ⇄ service
apps/playground/   # throwaway Laravel app for integration testing
deploy/            # Dockerfiles + compose (single-node and split topologies)
docs/              # architecture blueprint (00..10) + tech specs
tools/             # CI / contract-drift / codegen helpers

AI Safety & Security

Defense-in-depth around a generated query

Trusting an LLM's "this query is safe" is a non-starter. Safety is enforced by independent layers that don't trust each other.

🛡️

Dual SQL guard

Both the AI service and the package validate generated SQL. The package-side guard is authoritative: single-statement, SELECT / WITH only, blocked-verb list, comment / OUTFILE stripping, and an App-Map table allowlist. The Python guard uses a sqlglot AST with a lexical fallback.

🔒

Read-only execution

Queries run on a dedicated read-only connection with a SELECT-only re-check, a LIMIT / row cap, a statement timeout, and a READ ONLY session where the driver supports it.

🤝

Human-in-the-loop approval

Generated queries persist with a guard verdict and approval state; execution is gated on a separate query.approve capability.

🔑

HMAC service auth

Signed requests with clock-skew tolerance secure the boundary between the package and the AI service.

🕵️

PII masking

Logs are PII-masked on ingestion, before anything is stored or sent to a model.

📋

Capability gating + full audit

Every AI action resolves through a role capability and writes a capability.granted / capability.denied / action event to loc_audit_events.

What I Learned

The hard problems — and how I solved them

Depth over feature count: every architectural decision here is one I can defend end to end.

🎯  Making generated SQL provably safe

Trusting an LLM's "this query is safe" is a non-starter. The solution was defense-in-depth: parse the generated SQL into an AST, enforce a table allowlist derived from the discovered Application Map, re-validate independently on the execution side, and run on a physically read-only connection.

Even a query the AI claims is safe is blocked if it fails the guard — verified by tests that feed the guard destructive SQL labeled safe.

🔗  Keeping two languages honest across a network

A PHP package and a Python service must agree on every request and response shape. Making the OpenAPI spec the single source of truth — with a CI drift check — turned "did someone change the API?" from a runtime surprise into a failed build.

🔌  Running an AI system fully offline

Real model calls are slow, nondeterministic, and cost money. A provider abstraction with an echo implementation plus deterministic heuristics lets the entire system — RAG, NL→SQL, log RCA — run and be tested without any external API, while still allowing a real provider to be dropped in via config.

🧭  Grounding agents in an unknown host app

The package can't assume table or column names. The Discovery Engine's probes build an Application Map that every agent consults, so the same code works against any Laravel schema.

ⓘ  Honest framing

This project is presented as built and tested — five modules complete with 40 test files across Pest and pytest and a three-job CI — not as "deployed" or "in production."

Two items remain before a live demo: the LLM / embedding providers currently run on an offline echo stub (wiring a real provider is a config change), and there is no live MySQL end-to-end run in CI yet. The architecture, security model, and test coverage are the substance here; a recorded demo of a natural-language question returning a guarded, executed SELECT is the next step.
