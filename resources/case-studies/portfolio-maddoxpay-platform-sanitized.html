Wallet Engine

Dual wallet system — purpose-built per service type

A core architectural decision — two separate wallet systems with different balance types, different exception models, and different commission flows. Each wallet wraps every operation in a DB::beginTransaction() for atomicity.

◕ Main / Debit Wallet

  • Primary agent balance — funded via top-up (Cashfree, Zaakpay, manual admin credit)
  • Used for: Cash Deposit (AEPS), DMT transfers, PAN Card, BBPS, Recharge, FASTag, IRCTC, ITR
  • Custom exceptions: InsufficientDebitWalletBalanceException, NegativeBalanceException
  • Balance check → hasToPurchase() before any debit
  • Every debit creates a transactions record + MasterCommissionDistribution row
  • eMitra users are redirected away from top-up — they use credit wallet only
  • Admin can manually credit/debit agent wallets from the dashboard
🛠️ Service class: DebitWalletService::initiateOrderTransaction() — single entry point for all debit-wallet services

◕ Credit Wallet

  • Commission credit balance — automatically credited from commission distributions
  • Used for: AEPS Cash Withdrawal, AEPS Mini Statement, AEPS Balance Enquiry, MATM withdrawal
  • eMitra kiosk operators use credit wallet exclusively (blocked from main wallet)
  • Balance tracked via credit_wallet_transactions table with running balance column
  • isWalletTransfer flag controls whether balance is actually moved (vs. just recorded)
  • Custom exception: InsufficientDebitWalletBalanceException (shared), InvalidWalletOperationException
  • Balance readable at any point: walletRepository::getMyCreditBalance()
🛠️ Service class: CreditWalletService::initiateOrderTransaction() — 7 injectable repositories, handles commission distribution inline

Commission Architecture

3-tier hierarchical commission distribution

Every transaction — regardless of service — flows through the same commission distribution model. The hierarchy is agent → RM (Regional Manager) → SM (Super Manager) → MaddoxPay platform. Slabs are configurable per service per tier from the admin panel.

📈 Commission Hierarchy

MDX
MaddoxPay Platform

Platform margin after all distributions — configured as percentage or flat amount

SM
Super Manager (SM)

Top distributor in agent chain — earns override commission on every transaction below

RM
Regional Manager (RM)

Mid-level distributor — configurable commission on agent transactions

AG
Agent

Transaction-initiating user — earns base commission on every successful transaction

🔮 How Commission is Calculated

  • Service + transaction type → slab lookup by min_range / max_range matching transaction amount
  • Agent hierarchy walked via UserChainTrait / detectHierarchy() to determine SM/RM presence
  • Correct commission model selected: SuperDistributor → Distributor → Base
  • All percentage splits (mdx / sm / rm / agent) stored in MasterCommissionDistribution
  • AEPS commissions: SHA256 input + output + combined checksum written per calculation
  • eMitra users: override path via MdxCommCalculatorHelper::emitraServiceCommissionDetails()
  • Custom payment plan: if agent is on a plan, plan-tier rates applied instead of standard slabs

⚙️ Admin Commission Controls

  • MasterCommConfigController — set base slabs per service per transaction type
  • Distributor override: RM can set custom agent-level rates
  • Manager can adjust agent commission from AgentCommController
  • Commission logs visible in MIS with per-transaction breakdown
  • MS = ₹1 fixed (50/50 split); BE = zero (AEPS-specific rules)

📄 Commission Models

  • MasterCommission — base slab config per service
  • AepsCommissionSlab — AEPS base slabs
  • AepsDistributorCommissionSlab — RM slabs
  • AepsSuperDistributorCommissionSlab — SM+RM slabs
  • MasterCommissionDistribution — per-transaction record of all splits
  • MaddoxCommBasedPaymentPlan — custom plan config
  • MaddoxCommBasedPaymentPlanTransaction — plan usage tracking

🔎 User Chain Resolution

  • UserChainTrait — resolves the full agent → RM → SM hierarchy from URL chain parameter
  • Redis-cached per user+chain with hierarchy version bump on user tree changes
  • Prevents re-walking the parent tree on every request
  • Admin can impersonate any chain for reporting

Government Portal Integration

eMitra — Rajasthan Government Kiosk Portal

MaddoxPay is integrated as a service provider within the Rajasthan government's eMitra portal — allowing eMitra kiosk operators to access AEPS biometric banking directly from the government platform.

🔐 AES Encrypted SSO Redirect

  • eMitra portal redirects to MaddoxPay with AES-CBC encrypted encData payload
  • Decrypted server-side via AesMethod::aesDecrypt()
  • SSO token verified against eMitra SSO endpoint before any session is established
  • Kiosk operator details fetched and stored in session

⚟️ Circuit Breakers on B2B APIs

  • Two dedicated circuit breakers: emitra_b2b_transaction and emitra_verify_transaction
  • Prevents AEPS transactions from blocking when eMitra API is slow or down
  • ErrorCategorizer classifies failure types (timeout, auth, server error)
  • Circuit opens after threshold failures; auto-resets after cool-down window

📋 MD5 Checksums + Consumer Keys

  • B2B and verify requests include MD5 checksum of credential array (including SSOTOKEN)
  • Consumer keys generated using cryptographically secure randomness
  • Timestamps formatted as YmdHisv (millisecond precision)
  • Full request/response logged to emitra_api_logs channel

🔄 Reconciliation Job

  • ReconcileTransactionsJob — queued job for batch reconciliation
  • EmitraReconciliationService verifies eMitra-side status for pending/failed records
  • Force-cancel workflow with optional eMitra API call bypass
  • Full eMitra MIS report via EmitraMISController with date-range DataTables

👥 Dual User Type From One Controller

  • $user->is_emitra_user flag branches wallet, commission, and service logic throughout
  • eMitra session guard: transaction type restricted to active em_service_id
  • MS service ID re-resolved at runtime when offered under CW session
  • Graceful fallback: clone base service + override em_service_id if MS record missing

🗂 eMitra Data Schema

  • emitra_order_transactions — per-transaction eMitra settlement record
  • emitra_kiosk_requests — incoming redirect session records
  • mdx_emitra_services — mapping eMitra service IDs to Maddox services
  • Polymorphic transactions() morphTo via mdx_wallet_type / mdx_trans_id
System Architecture

How the entire platform is structured

A layered, repository-driven Laravel architecture — every service behind an interface, business logic in dedicated service classes, no DB calls from controllers.

1

Route Layer — Web + API

Separate route files per concern: service-routes (agent service routes), webhook-routes (webhooks + mobile API), auth-routes (auth + dashboard). Middleware groups enforce auth (IsAuthenticated), service subscription (IsServiceSubscribed), and active account status. CSRF-exempt webhook routes validated by provider signature instead.

service-routes webhook-routes IsServiceSubscribed middleware IsAuthenticated middleware
2

Controller Layer — Thin, Dependency-Injected

Controllers are dependency-injected via constructor. No Eloquent queries inside controllers — all data access delegated to repositories. Controllers orchestrate: validate request → call service → commit or rollback → return view/JSON. The most complex controller (AepsServicesController) has 20+ injected dependencies.

JoshController (base) ServiceBaseController Controller::middleware() Form Request validation
3

Service Layer — Business Logic & Third-Party Clients

All business logic lives in dedicated service classes. Gateway clients (AepsApiService, DMTService, EmitraApis, AxisPayoutService, etc.) encapsulate all HTTP communication, authentication, and response parsing. Wallet services (DebitWalletService, CreditWalletService) are the sole entry points for wallet operations. Commission services apply slab resolution and hierarchy detection.

AepsApiService (1600+ lines) EmitraApis DebitWalletService CreditWalletService EmitraTransactionService AepsCommissionService PayoutGatewayService FXPRechargeService
4

Repository Layer — All DB Access Behind Interfaces

Every model access is behind a repository interface registered in the service container. Repositories are injected into controllers and services — enabling easy swapping of implementations and clean unit-testability. Includes repositories for wallets, transactions, commission distributions, users, services, DMT remitters/beneficiaries, AEPS records, eMitra services, and more.

WalletRepositoryInterface TransactionRepositoryInterface CreditWalletTransactionRepository MasterCommissionDistributionRepository AepsTransactionRepository EmitraServiceRepository PayoutMoneyTransferRepository UsersRepositoryInterface
5

Database Layer — Relational + Extensible Schema

MySQL with a central transactions table + transaction_meta table — service-specific transaction details live in dedicated per-service tables (aeps_transactions, dmt_transactions, matm_transactions, emitra_order_transactions, etc.). The Transaction model exposes hasOne relations to each service-specific table for unified querying in MIS.

transactions transaction_meta credit_wallet_transactions master_commission_distributions aeps_transactions emitra_order_transactions payout_money_transfers nsdl_transactions
6

Queue + Jobs + Cache

Background jobs handle export generation (GenerateAepsExportJob), eMitra reconciliation (ReconcileTransactionsJob), and notification delivery. Redis caches user hierarchy chains (per user+chain, invalidated on user tree changes via User::bumpHierarchyVersion()). Activity logging is handled via ApiActivityLogService for all third-party API calls.

GenerateAepsExportJob ReconcileEmitraTransactionsJob Redis (hierarchy cache) ApiActivityLogService User::bumpHierarchyVersion()

Security

Security-first at every layer

🔐

AES-CBC Encryption

eMitra portal redirect payload encrypted with AES-CBC. Decrypted server-side — no plaintext credentials in URL or transit.

📋

SSO Token Verification

Every eMitra session validates SSO token against government endpoint before any session is established.

👆

Biometric PID Pipeline

RD device returns encrypted XML PID. Decrypted and parsed server-side — raw biometric data never stored or logged.

🔑

Backend Session Guards

eMitra transaction type restricted server-side by em_service_id — frontend bypass via direct POST returns 403.

🗂

Atomic Wallet Operations

All wallet debits/credits inside DB::beginTransaction() — balance check, wallet record, commission record all-or-nothing.

🔄

SHA256 Commission Audit

Input + output + combined SHA256 checksum on every commission calculation — tamper-evident audit log per transaction.

⚡

MD5 Checksums (eMitra)

eMitra B2B and verify requests include MD5 of credential array with SSOTOKEN — payload tampering invalidates checksum.

⚟️

Circuit Breakers

Two circuit breakers on eMitra endpoints. Trips open on repeated failures — prevents transaction flows from hanging on govt. API timeout.

📍

Geolocation Validation

Biometric 2FA locks agent lat/long. Haversine distance check on every transaction flags impossible location jumps.

🔓

Cartalyst Sentinel Auth

Role-based access control. All admin/manager/user routes gated. Each role has distinct permission sets enforced at route + controller level.

🛠️

JWT / Token Auth (APIs)

Paysprint gateway uses JWT authentication on every request. API tokens rotated per session. Mobile app API uses JWTAuth guard.

👤

MPIN Verification

Sensitive operations require MPIN confirmation from the agent. PIN stored hashed — never verified in plaintext.
