Project Overview

What was built

A complete Micro ATM banking feature — from scratch — integrated with a third-party biometric ATM SDK, enabling agents on the MaddoxPay platform to perform card-based cash withdrawals and balance enquiries at customer doorsteps using a biometric fingerprint reader.

💳

Cash Withdrawal

Agents can initiate amounts in configurable multiples. A dedicated popup SDK window handles biometric capture and card interaction, keeping the main application state clean.

📈

Balance Enquiry

Real-time account balance lookup via biometric authentication — no amount required. Commission-free by design, handled cleanly with a dedicated code path in the commission engine.

📱

Device Registration Portal

Agents register their MATM hardware device serial numbers before transacting. Full lifecycle: pending → approved / rejected → superseded, with admin review and re-submission support.

⚙️

Commission Engine

A slab-based, amount-ranged commission calculator that automatically detects the agent's hierarchy tier — Agent, Distributor (RM), or Super Distributor (SM) — and routes the right earnings to each level.

📋

Transaction Dashboard

A rich analytics view with nested Highcharts pie charts for CW/BE breakdowns by status, a 7-day bar chart for daily activity, summary stats, and an interactive transaction history table with instant repeat-transaction.

📄

Digital Receipts

Every completed transaction generates a printable, branded receipt page, accessible via encrypted URL. Automatically opened after the SDK callback fires, with a one-time localStorage token bridge.

A layered, event-driven architecture — the browser launches an isolated SDK popup, the Laravel backend orchestrates wallet and commission logic, and a webhook callback from the provider closes the transaction loop.

Engineering Decisions

Challenges & how they were solved

⚠️ Challenges Faced

  • The SDK callback uses inconsistent field names across SDK versions (e.g., clientRefID vs clientRef_Id vs clientRefId)
  • Callback arrives from the provider without auth headers — standard credential checks would block it
  • SDK must open in a separate popup — the payload cannot be embedded in a URL (too long + insecure)
  • Wallet debit for CW must be atomic — race conditions could cause double-debit
  • Commission calculation must handle 3 different user tiers with different slab tables
  • Device serial numbers must be globally unique across all users

✅ Solutions Implemented

  • Built a NormalizeCallbackPayload() method that gracefully resolves all known field name variants in priority order
  • Designed credential validation to allow empty-header callbacks through, falling back to DB-side reference ID matching for authenticity
  • Used a one-time localStorage token bridge — payload stored briefly and removed immediately after reading, isolating data between sessions
  • Wrapped wallet credit inside a DB transaction with custom exception types for insufficient balance, invalid operations, and negative balances
  • Built a hierarchy detector that selects the right Eloquent commission slab model at runtime based on SM/RM presence
  • Added a global uniqueness check on serial numbers before processing any registration attempt

MicroAtmCommissionService — CalculateCommission() — pseudocode 
FUNCTION CalculateCommission(serviceId, user, transactionType, amount):

    // Balance Enquiry earns no commission — short-circuit immediately
    IF transactionType == 'matm_be_transaction':
        RETURN BalanceEnquiryZeroCommissionResponse()

    // Detect agent's position in the distribution chain
    [hasSuperManager, hasRegionalManager] = DetectHierarchy(user)

    // Resolve correct commission slab model by hierarchy depth
    commissionModel = ResolveCommissionModel(hasSuperManager, hasRegionalManager)

    slab = commissionModel.Where('min_range', '<=', amount)
        .Where('max_range', '>=', amount)
        .First()

    // Build response and log with SHA-256 integrity checksum for audit trail
    response = BuildCommissionResponse(slab, amount, hasSuperManager, hasRegionalManager, transactionType)

    AuditLog.Write('matm_audit_channel', {
        output:         response,
        input_checksum: SHA256(JSON.encode(inputData)),
        elapsed_ms:     ElapsedTime()
    })

    RETURN response
SDK Callback Normaliser Gracefully handles all known SDK field name variants across versions
MicroAtmService — NormalizeCallbackPayload() — pseudocode 
// DEFENSIVE PATTERN: Normalize inconsistent callback field names across SDK versions.
// The external SDK uses different field name casings across versions —
// resolution uses priority-ordered null-coalescing to find the first non-null value.

FUNCTION NormalizeCallbackPayload(payload):

    // Reference ID — multiple known variants across SDK versions
    referenceId = Trim(String(
        payload['clientRefID']     // Variant A — JSON callback format
        ?? payload['clientRef_Id']  // Variant B — reqdata callback format
        ?? payload['clientRefId']   // Variant C
        ?? payload['ClientRefID']   // Variant D — uppercase
        ?? payload['referenceId']   // Fallback key name
        ?? ''
    ))

    // UTR / RRN — settlement reference number
    utr = String(
        payload['RRN']   // Retrieval Reference Number — primary
        ?? payload['rrn']
        ?? payload['utr']
        ?? ''
    )

    // Transaction status string
    statusText = String(
        payload['STATUS']    // Primary status field
        ?? payload['status']
        ?? payload['txnStatus']
        ?? ''
    )

    RETURN { referenceId, utr, statusText }
Frontend SDK Bridge One-time localStorage token securely passes payload to popup window
transaction.blade.php — LaunchMicroAtmSdk() — pseudocode 
// PATTERN: One-time localStorage token bridge for SDK popup payload.
// Opens popup immediately on user gesture (before async delay — avoids browser popup block),
// then passes encrypted payload via a temporary, auto-expiring token.

FUNCTION LaunchMicroAtmSdk(transactionType, amount):

    // Open popup BEFORE async operation — preserves user gesture context
    sdkWindow = Window.Open('about:blank', '_blank')

    // Initiate transaction on backend — receive encrypted SDK payload
    response = API.Post('/matm/initiate', { transactionType, amount })

    // Generate unique one-time token for localStorage bridge
    token = 'matm_' + Timestamp() + '_' + RandomString(8)

    // Store payload briefly — popup reads and immediately deletes it
    LocalStorage.Set('matmSdkPayload_' + token, JSON.encode(response.data))
    sdkWindow.location.href = sdkUrl + '?token=' + URLEncode(token)

    // Poll for popup close → reload page to show updated transaction state
    pollTimer = SetInterval(function():
        IF sdkWindow.closed:
            ClearInterval(pollTimer)
            Page.Reload()
    , 1000ms)

Security

Built secure by default

Security wasn't bolted on — it was part of every architectural decision, from credential handling to callback validation.

🔐

AES Header Encryption

Every SDK request header is encrypted with a time-bound epoch nonce — credentials never travel in plain text.

⛳

Constant-Time Comparison

Credential validation uses constant-time comparison throughout — immune to timing-based side-channel attacks on string comparison.

📋

Encrypted Receipt URLs

Transaction IDs in receipt URLs are encrypted via Laravel's Crypt — sequential IDs are never exposed to the client.

🚪

One-Time SDK Token

The localStorage bridge token is removed immediately after first read — the SDK payload cannot be replayed even if the storage key is observed.

🔒

Input Sanitisation

All inputs validated server-side: 10-digit mobile numbers, alphanumeric serial numbers, and enumerated field values.

👤

Mobile Number Masking

Transaction history always displays only the last 4 digits of the customer mobile number — PII protected in the UI.

📄

Full Audit Logging

Every stage — payload build, wallet creation, commission calculation, and callback receipt — writes to a dedicated audit log channel with SHA-256 input checksums.

⚡

Atomic Wallet Operations

Wallet debits run inside a database transaction with typed exception handling for insufficient balance, negative balance, and invalid operations — no partial states.

Development Journey

How the feature was shipped

Phase 1

API research & database design

Studied the Micro ATM SDK documentation, mapped out all callback field variants, and designed the two database tables with full audit-trail columns. Established the repository interfaces before writing any concrete code.

Phase 2

Service layer & encryption

Built the Micro ATM service to handle credential loading, AES-encrypted header construction, SDK payload assembly, callback credential validation, payload unwrapping, and field normalisation across SDK versions.

Phase 3

Commission engine

Implemented the multi-tier commission calculator with automatic hierarchy detection, three separate Eloquent slab models, a SHA-256 audit checksum on every calculation, and a fast-path short-circuit for Balance Enquiry.

Phase 4

Controllers, middleware & routing

Wired up both controllers with dependency injection, applied device registration and service subscription middleware, and defined all web + API routes including the unauthenticated webhook endpoint.

Phase 5

Frontend & SDK popup bridge

Designed the single-page transaction dashboard, built the localStorage token bridge for the SDK popup, integrated Highcharts for nested pie and 7-day bar charts, and added the repeat-transaction feature from the history table.

Phase 6

Device registration portal & user manual

Built the full device registration flow with all lifecycle states (pending / approved / rejected / superseded), a dedicated pending status page, and a rich HTML user manual covering every step of the service.
