Project Overview

What was built

A full-stack Aadhaar Enabled Payment System integration — enabling agents to perform biometric bank transactions for customers, with merchant onboarding, Bio-KYC, daily Two-Factor Authentication, and a parallel integration with Rajasthan's eMitra government portal for kiosk operators.

🤦

Merchant Onboarding (Multi-step KYC)

Agents register with Fingpay via a comprehensive KYC form — PAN, Aadhaar, shop address, bank settlement details, Pan image, masked Aadhaar image, and shop background photo — all assembled into a deeply nested API payload with S3 image uploads.

👆

Bio-KYC + Bank eKYC

Two-stage KYC: biometric fingerprint capture for bio-KYC, followed by a separate bank eKYC process. A dedicated FP097 response code triggers automatic redirect to eKYC page and sets bank_ekyc_status = 'pending'.

🔑

Daily Two-Factor Authentication

Agents complete a biometric 2FA every day before conducting transactions. 2FA status is verified by checking the transactions table for a same-day master_two_factor_auth success record. Geolocation (lat/long) is captured and stored at 2FA time.

💸

AEPS Transactions (CW, CD, MS, BE)

Four transaction types with differing wallet mechanics: Cash Withdrawal/Balance Enquiry/Mini Statement use the credit wallet, Cash Deposit uses the debit wallet. Each transaction captures IIN number, Aadhaar, biometric PID, geolocation, and full commission breakdown.

🏠

eMitra Portal Integration

Rajasthan government kiosk operators land on MaddoxPay via AES-encrypted redirect from the eMitra portal. SSO token is verified, kiosk details fetched, and B2B transactions executed with MD5 checksums — plus full eMitra receipt and MIS report generation.

🔧

3-Way Reconciliation & Circuit Breakers

Three-way reconciliation against Fingpay confirms transaction final status. Circuit breakers on both eMitra B2B and verify endpoints prevent cascade failures. The haversine algorithm validates distance between transaction location and registered shop coordinates.

System Architecture

How the system is structured

A deeply layered architecture spanning two gateways, two wallet systems, and a government portal — all behind one unified controller.

1

Controller — FingpayAepsServicesController (20+ injected dependencies)

The most dependency-rich controller on the platform. Manages the complete lifecycle: onboarding gate checks (onboard status, KYC status, bank eKYC, 2FA), service product views, aadhar info lookup, transaction initiation, and post-transaction receipt generation. Detects Emitra vs. regular users and routes wallet and commission logic accordingly. Backend guards prevent Emitra users from transacting outside their active session type (CW/CD/MS/BE scoped per eMitra service ID).

2

Fingpay API Service — AepsApiService

The Fingpay gateway client — 1600+ lines covering onboarding, OTP send/verify, Bio-KYC, KYC status check, Two-Factor Auth, four AEPS transaction types, transaction status, and three-way reconciliation. Biometric XML PID data is decrypted from the browser, parsed, and converted into Fingpay's required request format. Includes device serial number extraction, merchant PIN decryption, haversine geo-distance validation, and dynamic lat/long updates. UAT mode uses random test-case JSON files from public/testcase/aeps/ with weighted randomization (boosted 10000.json probability).

AepsApiService.php decryptBiometricData() biometricResponseCollection() threeWayReconApi() haversineDistance() updateLatLong()
3

eMitra API Service — EmitraApis (AES + Circuit Breakers)

The Rajasthan government eMitra gateway client. Incoming redirect data is AES-decrypted via AesMethod::aesDecrypt(). SSO tokens are verified against the eMitra SSO URL. Back-to-back (B2B) transactions and verification calls each have dedicated circuit breakers — if the endpoint trips, the circuit opens to prevent cascade failures. Checksums use MD5 of JSON-encoded credential arrays (including SSOTOKEN). Consumer keys are generated using SHA256 of mt_rand() + microtime(). Timestamps are formatted as YmdHisv (millisecond precision).

EmitraApis.php CircuitBreaker.php ErrorCategorizer.php AesMethod.php backToBackTransaction() verifyEmB2BTransaction() cancelTransaction()
4

Commission Engine — FingpayAepsCommissionService

A tiered, model-resolved commission calculator with SHA256 audit checksums. Detects agent hierarchy by walking up the user parent tree — if an SM is found, MasterFingPayAepsSuperDistributorCommission is used; if only RM exists, MasterFingPayAepsDistributorCommission; otherwise base MasterFingPayAepsCommission. Commission slabs matched by min_range / max_range with amount. Mini Statement returns a fixed ₹1 split; Balance Enquiry returns zero commission. For Emitra users, MdxCommCalculatorHelper::emitraServiceCommissionDetails() is called instead.

FingpayAepsCommissionService.php detectHierarchy() resolveCommissionModel() buildCommissionResponse() MdxCommCalculatorHelper (Emitra)
5

Emitra Wallet Service — EmitraTransactionService (dual wallet orchestration)

Orchestrates wallet operations for eMitra users. Debit transactions (Cash Deposit) go to the main wallet via initiateDebitTransaction(). Credit transactions (CW/MS/BE) go to the credit wallet via initiateCreditTransaction() — which includes special MS service ID resolution logic: Mini Statement sessions offered under the CW eMitra service ID are re-resolved to the dedicated MS service ID, with a graceful fallback clone. Post-transaction, it calls back to eMitra's B2B API and verify endpoint to settle the transaction in the government system. Also supports force-cancel with eMitra API call bypass.

EmitraTransactionService.php initiateDebitTransaction() initiateCreditTransaction() processEmitraTransaction() cancelEmitraTransaction() syncAepsEmitraBaseWalletStatus() resolveBaseWalletTransaction()
6

Repository Layer (7+ interfaces) + Database Design

All data access behind interfaces. FingpayAepsTransactions table stores transaction metadata with dual wallet resolution (CD uses transactions table, others use credit_wallet_transactions). The model exposes a computed resolved_transaction accessor that automatically returns the right wallet record based on txn_type. eMitra has its own emitra_order_transactions table tracking SSO IDs, kiosk codes, eMitra service IDs, revenue heads, and wallet types with a polymorphic transactions() morphTo relation.

Dual User Mode

One codebase, two completely different flows

The same controller detects whether the logged-in user is a Maddox agent or an eMitra kiosk operator and branches the entire wallet, commission, and API logic accordingly.

👤 Maddox Agent Mode

Regular agent on MaddoxPay

  • Commission calculated by FingpayAepsCommissionService using slab-based hierarchy detection
  • CW/MS/BE → Credit Wallet via CreditWalletService
  • CD → Debit Wallet via DebitWalletService
  • WhatsApp notification sent after transaction via WhatsAppService
  • Full AEPS product view with transaction history, DataTables, and receipt
  • No eMitra service ID scoping — can use all 4 transaction types freely
🏠 eMitra Kiosk Operator Mode

Government kiosk agent (Rajasthan eMitra)

  • Redirected from eMitra portal with AES-encrypted payload; SSO token verified
  • Commission calculated by MdxCommCalculatorHelper::emitraServiceCommissionDetails()
  • Wallet via EmitraTransactionService — which also triggers eMitra B2B API
  • Transaction type restricted to active eMitra session service ID (backend guard)
  • MS allowed under CW eMitra session with re-resolved service ID
  • Transaction confirmed by eMitra verify endpoint; receipt printed via eMitra receipt URL

Transaction Mechanics

Dual wallet engine — type-resolved at runtime

A single initiateTransaction() method branches into completely different wallet flows depending on transaction type — solved by a type-to-config map resolved at runtime.

🟡 Debit Wallet (Main Wallet)

  • Used for Cash Deposit (CD) only — agent funds the deposit
  • Calls DebitWalletService::initiateOrderTransaction()
  • Emitra: calls EmitraTransactionService::initiateDebitTransaction()
  • Exception types: InsufficientDebitWalletBalanceException, NegativeBalanceException
  • All wrapped in DB::beginTransaction() for atomicity

🟩 Credit Wallet

  • Used for CW, MS, BE — agent's credit balance is used
  • Calls CreditWalletService::initiateOrderTransaction()
  • Emitra: EmitraTransactionService::initiateCreditTransaction()
  • Commission flag: isCommission = ($type !== 'BE') — BE has zero commission
  • Credit balance checked via walletRepository::getMyCreditBalance()

// Detect hierarchy by walking up the user parent tree
[$hasSM, $hasRM] = $this->detectHierarchy($user);

// Resolve the correct commission model by hierarchy presence
$model = $this->resolveCommissionModel($hasSM, $hasRM);
// → MasterFingPayAepsSuperDistributorCommission  (SM + RM present)
// → MasterFingPayAepsDistributorCommission        (RM only)
// → MasterFingPayAepsCommission                   (standalone agent)

$slab = $model::where('min_range', '<=', $amount)
    ->where('max_range', '>=', $amount)
    ->first();

$response = $this->buildCommissionResponse($slab, $amount, $hasSM, $hasRM, $transType);

EmitraTransactionService.php — initiateCreditTransaction() — MS re-resolution
// MS is offered under the CW session, so always resolve it by the configured MS service ID.
// This is a key nuance: the kiosk_request.service_id will be the CW eMitra service,
// but the transaction must be logged against the MS eMitra service.
$resolvedServiceId = $type === 'MS'
    ? config('services.emitra.services.aeps_ms')
    : $baseService->em_service_id;

$serviceDetail = $this->emitraServiceRepository
    ->getServiceByEmitraServiceId($resolvedServiceId);

// Graceful fallback: if MS service record is not found (env mismatch),
// clone the CW base service but override the em_service_id so the eMitra API
// receives the correct MS service ID.
if (!$serviceDetail && $type === 'MS' && $baseService) {
    $serviceDetail = clone $baseService;
    $serviceDetail->em_service_id = $resolvedServiceId;
    $serviceDetail->paymode = null;
}

FingpayAepsServicesController.php — eMitra backend session guard
// BACKEND GUARD: Prevent unauthorized service types for Emitra users.
// Even if the frontend allows a type, the backend validates against the
// active Emitra session's em_service_id — a server-side enforcement.
if (!empty($user->is_emitra_user)) {
    $serviceInfo = app('GlobalEmitraServiceInfo');
    $allowed = false;

    if ($type === 'MS' && $serviceInfo && (
        $serviceInfo->em_service_id == config('services.emitra.services.aeps_ms') ||
        $serviceInfo->em_service_id == config('services.emitra.services.aeps_cw')  // MS under CW session
    )) {
        $allowed = true;
    }

    // ... similar checks for CW, CD, BE ...

    if (!$allowed) {
        return response()->json([
            'success'  => false,
            'message'  => 'Unauthorized transaction type for your current eMitra session.',
        ], 403);
    }

Engineering Decisions

Hardest problems & how they were solved

⚠️ The Hard Problems

  • Two completely different user types (Maddox agents vs eMitra kiosk operators) using the same controller — requiring branched wallet, commission, and API logic throughout
  • Mini Statement sessions are offered under the eMitra CW service ID — the transaction must still be logged against the MS service ID or eMitra settlement fails
  • Biometric XML PID data arrives from the browser already encrypted (from the RD device) and must be decrypted, parsed, and re-formatted before any API call
  • FP097 bank eKYC response can arrive during any Fingpay API call — needed a centralized handler usable from any controller or service
  • Cash Deposit uses debit wallet; all other AEPS types use credit wallet — must be determined at runtime and the correct exception types handled per path
  • eMitra B2B and verify API calls can fail silently or time out — without circuit breakers, every Fingpay transaction would hang waiting for the government API
  • Commission correctness is critical — a wrong split would silently under/over-pay agents. No native audit trail for commission calculations existed.

✅ Solutions Implemented

  • Built a clean runtime branch: $user->is_emitra_user flag checked at every decision point — commission, wallet type, service info, view routing — keeping both paths in one controller
  • Implemented MS service ID re-resolution in EmitraTransactionService with a graceful clone fallback when the MS service record is missing in a non-production environment
  • Built decryptBiometricData() → biometricResponseCollection() pipeline: decrypt PID → extract XML fields → map to Fingpay's exact key names — all before the API call
  • Extracted FP097 logic into FingpayAepsResponseTrait — a reusable trait that updates eKYC status and returns the correct redirect for AJAX and non-AJAX requests
  • Transaction type → wallet config map: ['CW'=>'credit', 'CD'=>'debit', 'BE'=>'credit', 'MS'=>'credit'] resolved before DB::beginTransaction() — correct exception type caught per branch
  • Dedicated CircuitBreaker instances per endpoint (emitra_b2b_transaction, emitra_verify_transaction) — trips open after repeated failures, preventing AEPS transactions from blocking on a government API timeout
  • SHA256 checksums on both commission input and output (plus a combined hash) written to a dedicated aeps_commission_new_slab log channel for every transaction — tamper-proof audit trail
Security

Security measures at every layer

🔐

AES Encrypted Redirect

eMitra portal sends session data as AES-encrypted encData. Decrypted server-side via AesMethod::aesDecrypt() — plaintext never visible in transit.

📋

SSO Token Verification

Every eMitra session verifies the SSO token against the eMitra SSO endpoint before any kiosk action is allowed — invalid or expired tokens are rejected.

🤦

Biometric PID Encryption

RD devices return encrypted XML PID data. The server decrypts and validates PID before forwarding to Fingpay — raw biometric data never stored.

🔑

eMitra Session Guard

Backend checks is_emitra_user + active em_service_id to enforce transaction type restrictions — frontend cannot bypass with a direct POST.

✅

MD5 Checksums (eMitra)

eMitra B2B and verify transactions include MD5 checksums of credential arrays including SSOTOKEN — tampers with request payload would invalidate the checksum.

🔄

SHA256 Commission Audit

Every commission calculation writes input/output/combined SHA256 checksums to a dedicated log — provides tamper-evident record of all commission decisions.

🗂

Atomic Wallet Operations

All wallet debits/credits run inside DB::beginTransaction() — commission calculation, wallet record creation, and AEPS transaction record are all-or-nothing.

⚟️

Circuit Breakers

Two circuit breakers prevent the Fingpay AEPS flow from blocking on eMitra government API failures — trips after threshold failures, logs error category via ErrorCategorizer.

📍

Geolocation Validation

Transaction lat/long is captured at 2FA time and reused per-transaction. Haversine distance calculation detects impossible location jumps between 2FA and transaction.

Development Journey

How this was built — phase by phase

Phase 1

Research, gateway analysis & database design

Studied Fingpay AEPS API documentation, mapped all onboarding and transaction endpoints, and designed the full schema: fingpay_aeps_onboard, fingpay_aeps_kyc, fingpay_aeps_two_fa, fingpay_aeps_transactions — with deliberate dual-wallet resolution columns baked in from the start.

Phase 2

AepsApiService — Fingpay gateway client (1600+ lines)

Built the full Fingpay API client covering all onboarding, KYC, 2FA, and transaction operations. Implemented biometric XML PID decryption pipeline, device serial number extraction from multiple RD device formats, merchant PIN decryption, and haversine geo-distance calculation. UAT mode with weighted JSON test-case randomization for dev/staging.

Phase 3

Merchant onboarding flow & multi-step KYC views

Built the multi-step onboarding form, S3 document upload integration, status-based gate checks at the controller level, and the Bio-KYC + bank eKYC flows with the FingpayAepsResponseTrait for centralized FP097 handling. Wired all KYC status checks into the servicesList() gate.

Phase 4

Commission engine with SHA256 audit trail

Built the three-tier commission service with hierarchy detection, slab-based model resolution, percentage calculation, and fixed responses for MS/BE. Added SHA256 checksum logging (input + output + combined) to the dedicated aeps_commission_new_slab log channel for every calculation.

Phase 5

Transaction engine — dual wallet, atomic operations

Wired up the complete transaction initiation flow with DB transaction wrapping, type-branched wallet service calls, all custom exception types, geolocation from 2FA record, and the full FingpayAepsTransactions record creation with commission splits. Added WhatsApp notifications on success.

Phase 6

eMitra government portal integration

Integrated the eMitra gateway: AES redirect decryption, SSO token verification, kiosk detail fetching, B2B transaction with MD5 checksum, verify endpoint, and cancel with refund. Built the EmitraServicesController service router and the EmitraTransactionService dual wallet orchestrator. Added circuit breakers to both eMitra API endpoints.

Phase 7

Dual-mode unification, edge cases & MIS

Unified both user types in the single controller: eMitra session guards, MS service ID re-resolution, the eMitra-specific commission branch, and view routing for onboarding vs. CW sessions. Built eMitra MIS reports with DataTables, AEPS transaction export, thermal receipt printing, and the complete admin transaction management views.
