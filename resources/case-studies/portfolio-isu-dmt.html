Project Overview

What was built

A complete Domestic Money Transfer (DMT) feature — integrated with IServeU's DMT Lite (IMPS) gateway — enabling agents on MaddoxPay to register customers as remitters, add and verify bank beneficiaries via penny drop, and execute real-time money transfers with automatic commission splits.

👤

Remitter Registration

Agents register customer senders via a mobile lookup → details form → OTP verification flow. A ₹10 wallet debit is charged on first-time registration, tracked to prevent double-charging.

🏦

Beneficiary Management

Per-remitter beneficiary pages with add / soft-delete support. Each beneficiary is linked to a bank from a master bank list. Up to the configured limit of beneficiaries per remitter.

✅

Penny Drop Verification

Two-step account verification: first an OTP is sent to the remitter's mobile, then a penny-drop transaction confirms the beneficiary's bank account. Only verified beneficiaries can receive transfers.

💸

Money Transfer (IMPS)

Agents initiate real-time IMPS transfers with automatic wallet debit, commission calculation, and order tracking. Orders are multi-transaction containers — a single order can have multiple transfer attempts.

⚙️

Commission Engine

A fully configurable, tiered commission system: agents earn a per-slab rate, with distributor (RM) and super-distributor (SM) shares calculated and distributed automatically per transaction.

📋

Transaction Receipts & History

Printable, branded receipts per transaction, accessible via encrypted order IDs. A rich "My Orders" page with DataTables-powered filtering, pagination, and per-order transaction drill-down.

Code Architecture

Layer-by-layer breakdown

1

HTTP Controllers (3 focused controllers)

IsuDmtRemitterController owns the entire customer onboarding lifecycle — mobile lookup, OTP dispatch, OTP verification, registration fee charging, and the resulting DataTables remitter list. IsuDmtBeneficiaryController handles beneficiary CRUD, the penny-drop OTP step, and bank list resolution. IsuDmtTransactionController drives transfers, order creation, and the inbound webhook callback.

IsuDmtRemitterController.php IsuDmtBeneficiaryController.php IsuDmtTransactionController.php
2

Service Layer — two-tier design

ImpsLiteService is the low-level IServeU HTTP client — handles credential loading, AES-encrypted header construction via EncDecService, and exposes all gateway operations: getCustomer, registerCustomer, sendOtp, addBeneficiary, pennyDrop, moneyTransfer, and checkTransactionStatus. Headers are rebuilt per-request for freshness. ImpsLiteServiceEnhanced wraps the base service with full onboarding flow orchestration — automatically routing through CASE 1 (not found → register), CASE 2A (unverified → re-register), and CASE 2B (verified → proceed) with cache-backed state management.

ImpsLiteService.php ImpsLiteServiceEnhanced.php EncDecService.php DebitWalletService.php
3

Repository Pattern (3 interfaces + implementations)

All database access is behind interfaces — keeping controllers free of Eloquent. IsuDmtRemitterRepository handles remitter CRUD, verified-scope queries, and DataTable query builders. IsuDmtBeneficiaryRepository manages per-remitter beneficiary queries with soft-delete awareness. IsuDmtOrderTransactionRepository covers order transaction creation, lookup by reference ID, callback-identifier resolution, and locking-for-update patterns.

IsuDmtRemitterRepository.php IsuDmtBeneficiaryRepository.php IsuDmtOrderTransactionRepository.php
4

Database Design (4 tables)

isu_dmt_remitters stores customer sender profiles with OTP verification state, transfer limits, and registration fee tracking columns (added via a later migration). isu_dmt_beneficiaries tracks bank account details with soft-delete and per-account verification status. isu_dmt_orders is the parent container per transfer session. isu_dmt_order_transactions captures every individual transfer attempt — including full commission splits (provider, MDX, user, maddox), UTR, gateway status code, and raw payloads.

isu_dmt_remitters isu_dmt_beneficiaries isu_dmt_orders isu_dmt_order_transactions
5

Frontend Views (5 Blade templates)

The remitter management page uses DataTables with server-side filtering by name and mobile. The money transfer page provides a step-based flow with inline validation. The beneficiary page handles both the add form and penny-drop verification in a single dynamic view. Registration is a multi-step wizard (mobile lookup → details form → OTP → result). Receipts are printable, branded, and accessed via encrypted order IDs.

remitter.blade.php beneficiary.blade.php money-transfer.blade.php receipt.blade.php my-order.blade.php
6

Routing (15+ named routes)

All routes live under the user.isu-dmt prefix group with IsServiceSubscribed:48 middleware. Separate named routes for each step of remitter registration, beneficiary operations (add, fetch, delete, verify, penny-drop OTP), and transfer flows. The webhook callback endpoint is public (no auth), with transaction authenticity verified by matching reference_id in the database.

Code Highlights

Key engineering decisions

Representative snippets showing design patterns, security measures, and architectural choices applied throughout the integration.

AES Header Construction Headers rebuilt per-request with fresh epoch — prevents replay attacks
ImpsLiteService.php — rebuildHeaders() 
/**
 * Re-create Authorization headers with a fresh epoch timestamp.
 * Called before each request — ensures time-bound credentials
 * cannot be replayed even if intercepted.
 */
public function rebuildHeaders(): void
{
    $this->headers = [
        'header_secrets' => $this->encDecService->encryptRequest([
            'client_id'     => $this->client_id,
            'client_secret' => $this->client_secret,
            'epoch'         => (string) time(),  // fresh every call
        ], $this->enc_key),
        'pass_key'       => $this->pass_key,
        'Content-Type'   => 'application/json',
    ];
}
Onboarding Orchestration Automatic KYC-state routing with three distinct flows
ImpsLiteServiceEnhanced.php — processCompleteOnboarding() 
/**
 * Automatically routes the customer through the correct onboarding case:
 *   CASE 1:  Customer Not Found  → Send OTP → Register
 *   CASE 2A: Not Verified        → Send OTP → Re-register
 *   CASE 2B: Already Verified    → Direct Access (no re-registration)
 */
public function processCompleteOnboarding(
    object $user,
    string $aadharNo = '',
    string $otp = '123456',
    bool   $autoRegister = true
): array {
    // Cache-backed state: avoids redundant API calls within the same session
    $cacheKey = self::CACHE_PREFIX . $user->id . ':flow';

    $getCustomerResponse = $this->baseService->getCustomer($user);

    if (!$getCustomerResponse['success']) {
        return $this->formatFlowResponse(false, '...', 'ERROR', 'RETRY_GET_CUSTOMER', null, false);
    }

    $customerData = $getCustomerResponse['data'] ?? [];

    // Route by KYC state:
    if ($customerData['kyc_verified'] === true) {
        return $this->formatFlowResponse(true, 'Verified', 'CASE_2B', 'PROCEED', $customerData, true);
    }

    return $this->handleUnverifiedCustomer($user, $customerData, $aadharNo, $otp);
}

Callback Safety Dual-identifier lookup with pessimistic locking prevents race conditions
IsuDmtOrderTransactionRepository.php — callback lookup 
/**
 * Match incoming callback to an order transaction by any known identifier.
 * Uses OR logic — handles cases where one field may be absent from the callback.
 * lockForUpdate() prevents double-processing if duplicate callbacks arrive.
 */
public function getOrderTransactionForCallbackIdentifiers(
    ?string $ackno = null,
    ?string $provider_txn_id = null
) {
    $query = $this->model->newQuery()->lockForUpdate();

    if (!empty($ackno)) {
        $query->where('ackno', $ackno);
    }
    if (!empty($provider_txn_id)) {
        if (!empty($ackno)) {
            $query->orWhere('provider_txn_id', $provider_txn_id);
        } else {
            $query->where('provider_txn_id', $provider_txn_id);
        }
    }
    return $query->first();
}
Engineering Decisions

Challenges & solutions

⚠️ Challenges Faced

  • IServeU customer lookup returns three distinct KYC states — each requiring a completely different onboarding path
  • AES-encrypted headers contain a timestamp — stale headers cause gateway rejections in long-lived process contexts
  • Registration ₹10 fee must be charged exactly once — even if the OTP step is retried or the request is replayed
  • Webhook callbacks can arrive without consistent field names across gateway versions
  • Duplicate callbacks from IServeU could cause double wallet credits if not guarded
  • Penny-drop OTP needs a two-step flow — OTP send and OTP confirm are separate HTTP calls with a shared reference ID

✅ Solutions Implemented

  • Built ImpsLiteServiceEnhanced with a named-case orchestrator: CASE_1 (not found), CASE_2A (unverified), CASE_2B (verified) — each with explicit next_action routing
  • Implemented rebuildHeaders() called before every outbound HTTP request, ensuring a fresh epoch timestamp is always embedded
  • Added a hasRemitterRegistrationFeeBeenCharged() guard checked before every wallet debit, backed by a dedicated DB column added via migration
  • Applied normalizeCallbackPayload() pattern (consistent with other IServeU integrations) with priority-ordered field resolution
  • Used lockForUpdate() inside the callback handler's DB query — pessimistic locking prevents two simultaneous callbacks from both updating the same record
  • Session-persisted reference_id from OTP-send step, reused at OTP-confirm step without re-calling the IServeU API
Security

Secure at every layer

Every decision — from API headers to DB queries to UI output — was made with security as a first-class concern.

🔐

AES-Encrypted Headers

Every gateway request carries header_secrets — AES-encrypted credentials + time-bound epoch. Rebuilt per request; credentials never in plain HTTP fields.

⛳

Config Validation on Boot

validateConfiguration() throws on startup if any credential is missing — service cannot be instantiated with incomplete configuration.

🔒

Encrypted Receipt URLs

Order IDs in receipt URLs are wrapped with Laravel's Crypt::encryptString() — raw database IDs are never exposed in browser URLs.

📋

Full Input Validation

All controller inputs validated server-side: mobile as digits:10, amounts as numeric|min:1, account numbers and IFSC codes with regex patterns.

🗂

Pessimistic Locking

Callback handler uses lockForUpdate() — concurrent duplicate callbacks cannot both update the same transaction record.

⚡

Atomic Wallet Debits

All wallet operations run inside database transactions with typed exception handling — partial states are impossible.

👤

ID Obfuscation

All remitter and beneficiary IDs passed via URL are encrypted/decrypted using encrypt_id() / decrypt_id() helpers — sequential enumeration is blocked.

📄

Idempotent Fee Guard

Registration fee checked before every debit attempt — a dedicated DB flag prevents the ₹10 from being charged more than once per remitter.

Development Journey

How the feature was shipped

Phase 1

Gateway research & database design

Studied the IServeU DMT Lite API documentation, mapped out all three customer KYC states, and designed four database tables with full audit-trail columns. Defined repository interfaces before writing any concrete code.

Phase 2

Core service layer — ImpsLiteService

Built the low-level gateway client with AES header construction, per-environment URL resolution, startup configuration validation, and all seven API operations: get-customer, register-customer, send-OTP, add-beneficiary, penny-drop, money-transfer, and status-check.

Phase 3

Enhanced orchestration — ImpsLiteServiceEnhanced

Wrapped the base service with a full onboarding flow orchestrator — automatic case detection, cache-backed state management for session continuity, and standardised flow-response formatting with explicit next_action directives.

Phase 4

Controllers, repositories & routing

Wired up all three controllers with full dependency injection, applied IsServiceSubscribed:48 middleware, and defined 15+ named routes across remitter registration, beneficiary management, transfer, and callback handling.

Phase 5

Commission engine integration

Integrated the MdxCommCalculatorHelper for ISU DMT rate lookups, wiring up the three-tier commission splits (agent / RM / SM / platform) into the order transaction model with full per-column breakdown for reporting.

Phase 6

Frontend views & registration fee migration

Built five Blade views covering the complete user journey. Added a follow-up migration to track registration fee state on existing remitter records, and refined the fee-guard logic to be fully idempotent across OTP retries and callback replays.
