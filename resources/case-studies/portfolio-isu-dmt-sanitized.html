Project Overview

What was built

A complete Domestic Money Transfer (DMT) feature — integrated with an IMPS-based money transfer gateway — enabling agents on MaddoxPay to register customers as remitters, add and verify bank beneficiaries via penny drop, and execute real-time money transfers with automatic commission splits.

👤

Remitter Registration

Agents register customer senders via a mobile lookup → details form → OTP verification flow. A one-time registration fee is charged from the agent wallet at first-time registration, with an idempotency guard to prevent double-charging.

🏦

Beneficiary Management

Per-remitter beneficiary pages with add and soft-delete support. Each beneficiary is linked to a bank from a master bank list, with a configurable limit per remitter.

✅

Penny Drop Verification

Two-step account verification: first an OTP is sent to the remitter's mobile, then a penny-drop transaction confirms the beneficiary's bank account. Only verified beneficiaries can receive transfers.

💸

Money Transfer (IMPS)

Agents initiate real-time IMPS transfers with automatic wallet debit, commission calculation, and order tracking. Orders are multi-transaction containers — a single order can have multiple transfer attempts.

⚙️

Commission Engine

A fully configurable, tiered commission system: agents earn a per-slab rate, with distributor (RM) and super-distributor (SM) shares calculated and distributed automatically per transaction.

📋

Transaction Receipts & History

Printable, branded receipts per transaction, accessible via encrypted order IDs. A rich "My Orders" page with DataTables-powered filtering, pagination, and per-order transaction drill-down.

Code Architecture

Layer-by-layer breakdown

1

HTTP Controllers (3 focused controllers)

The remitter controller owns the complete customer onboarding lifecycle — mobile lookup, OTP dispatch, OTP verification, registration fee charging, and the resulting DataTables remitter list. The beneficiary controller handles beneficiary CRUD, the penny-drop OTP step, and bank list resolution. The transaction controller drives transfers, order creation, and the inbound webhook callback.

RemitterController BeneficiaryController TransactionController
2

Service Layer — two-tier design

The gateway client service is the low-level HTTP adapter — handles credential loading, AES-encrypted header construction via an encryption service, and exposes all gateway operations: get-customer, register-customer, send-OTP, add-beneficiary, penny-drop, money-transfer, and check-status. Headers are rebuilt per-request for freshness. An enhanced orchestration service wraps the base client with full onboarding flow routing — automatically handling three KYC state cases (not found, unverified, verified) with cache-backed state management.

GatewayClientService OnboardingOrchestrationService EncryptionService DebitWalletService
3

Repository Pattern (3 interfaces + implementations)

All database access is behind interfaces — keeping controllers free of Eloquent. The remitter repository handles CRUD, verified-scope queries, and DataTable query builders. The beneficiary repository manages per-remitter beneficiary queries with soft-delete awareness. The order transaction repository covers creation, lookup by reference ID, callback-identifier resolution, and pessimistic locking patterns.

RemitterRepositoryInterface BeneficiaryRepositoryInterface OrderTransactionRepositoryInterface
4

Database Design (4 tables)

The remitters table stores customer sender profiles with OTP verification state, transfer limits, and registration fee tracking columns. The beneficiaries table tracks bank account details with soft-delete and per-account verification status. The orders table is the parent container per transfer session. The order transactions table captures every individual transfer attempt — including full commission splits, UTR, gateway status code, and raw payloads.

dmt_remitters dmt_beneficiaries dmt_orders dmt_order_transactions
5

Frontend Views (5 Blade templates)

The remitter management page uses DataTables with server-side filtering by name and mobile. The money transfer page provides a step-based flow with inline validation. The beneficiary page handles both the add form and penny-drop verification in a single dynamic view. Registration is a multi-step wizard (mobile lookup → details form → OTP → result). Receipts are printable, branded, and accessed via encrypted order IDs.

Routing (15+ named routes)

All routes live under a DMT-specific prefix group with a service subscription middleware. Separate named routes cover each step of remitter registration, beneficiary operations (add, fetch, delete, verify, penny-drop OTP), and transfer flows. The webhook callback endpoint is public (no CSRF), with transaction authenticity verified by matching reference IDs in the database.

Architecture Patterns

Key engineering decisions

Pseudocode representations of the design patterns, security measures, and architectural choices applied throughout the integration.

Time-Bound Header Construction Headers rebuilt per-request with fresh epoch — prevents replay attacks
GatewayClientService — RebuildGatewayHeaders() — pseudocode 
// ARCHITECTURE PATTERN: Time-bound header reconstruction
// Re-create encrypted Authorization headers with a fresh epoch timestamp.
// Called before each outbound gateway request — ensures time-bound credentials
// cannot be replayed even if intercepted in transit.

FUNCTION RebuildGatewayHeaders():

    encryptedSecrets = EncryptionService.Encrypt({
        client_id:     this.clientId,
        client_secret: this.clientSecret,
        epoch:         CurrentTimestamp(),  // fresh on every call
    }, this.encryptionKey)

    this.headers = {
        'authorization': encryptedSecrets,
        'access_key':    this.accessKey,
        'Content-Type':  'application/json',
    }
Onboarding Orchestration Automatic KYC-state routing with three distinct flows
OnboardingOrchestrationService — ProcessOnboarding() — pseudocode 
// ARCHITECTURE PATTERN: KYC-state routing with three distinct flows
// Automatically routes the customer through the correct onboarding case:
//   CASE 1:  Customer Not Found   → Send OTP → Register
//   CASE 2A: Not KYC-Verified     → Send OTP → Re-register
//   CASE 2B: Already KYC-Verified → Direct Access (no re-registration)

FUNCTION ProcessOnboarding(user, aadharNo, otp, autoRegister):

    // Cache-backed state: avoids redundant API calls within the same session
    cacheKey = CACHE_PREFIX + user.id + ':flow'

    customerResponse = GatewayService.GetCustomer(user)

    IF NOT customerResponse.success:
        RETURN ErrorResponse('RETRY_GET_CUSTOMER')

    customerData = customerResponse.data

    // Route by KYC state:
    IF customerData.kyc_verified == true:
        RETURN FlowResponse(success=true, case='CASE_2B', action='PROCEED', data=customerData)

    RETURN HandleUnverifiedCustomer(user, customerData, aadharNo, otp)
Idempotent Fee Guard Registration fee charged exactly once — never double-billed across retries or replays
RemitterController — registration fee idempotency guard — pseudocode 
// IDEMPOTENCY GUARD: Registration fee charged exactly once per remitter,
// even if the OTP step is retried or the request is replayed.

IF NOT HasRegistrationFeeBeenCharged(remitter):

    // Balance gate before any debit attempt
    IF NOT WalletRepository.HasSufficientBalance(user.id, registrationFee):
        RETURN ErrorResponse(422, 'Insufficient wallet balance for registration fee.')

    // Atomic debit with typed transaction code for audit trail
    DebitWalletService.ProcessTransaction(
        serviceId:       this.serviceId,
        transactionType: 'remitter_registration',  // audit trail identifier
        user:            user,
        amount:          registrationFee,
        direction:       'debit'
    )
Callback Safety Dual-identifier lookup with pessimistic locking prevents race conditions
OrderTransactionRepository — FindTransactionForCallback() — pseudocode 
// SAFETY PATTERN: Dual-identifier lookup with pessimistic locking.
// Match incoming callback to an order transaction by any known identifier.
// Uses OR logic — handles cases where one field may be absent from the callback.
// LockForUpdate() prevents double-processing if duplicate callbacks arrive.

FUNCTION FindTransactionForCallback(acknowledgeId, providerTxnId):

    query = OrderTransactionModel.NewQuery().LockForUpdate()

    IF acknowledgeId is not empty:
        query.Where('acknowledge_id', acknowledgeId)

    IF providerTxnId is not empty:
        IF acknowledgeId is not empty:
            query.OrWhere('provider_txn_id', providerTxnId)
        ELSE:
            query.Where('provider_txn_id', providerTxnId)

    RETURN query.First()
Engineering Decisions

Challenges & solutions

⚠️ Challenges Faced

  • Gateway customer lookup returns three distinct KYC states — each requiring a completely different onboarding path
  • AES-encrypted headers contain a timestamp — stale headers cause gateway rejections in long-lived process contexts
  • Registration fee must be charged exactly once — even if the OTP step is retried or the request is replayed
  • Webhook callbacks can arrive without consistent field names across gateway versions
  • Duplicate callbacks from the gateway could cause double wallet credits if not guarded
  • Penny-drop OTP needs a two-step flow — OTP send and OTP confirm are separate HTTP calls with a shared reference ID

✅ Solutions Implemented

  • Built an onboarding orchestration service with a named-case router: CASE_1 (not found), CASE_2A (unverified), CASE_2B (verified) — each with explicit next-action routing
  • Implemented a header rebuild method called before every outbound HTTP request, ensuring a fresh epoch timestamp is always embedded
  • Added an idempotency guard checked before every wallet debit, backed by a dedicated DB column added via migration
  • Applied a payload normalization pattern with priority-ordered field resolution across all known callback field name variants
  • Used LockForUpdate() inside the callback handler's DB query — pessimistic locking prevents two simultaneous callbacks from both updating the same transaction
  • Session-persisted reference ID from OTP-send step, reused at OTP-confirm step without re-calling the gateway
Security

Secure at every layer

Every decision — from API headers to DB queries to UI output — was made with security as a first-class concern.

🔐

AES-Encrypted Headers

Every gateway request carries encrypted credentials + a time-bound epoch. Rebuilt per request — credentials never in plain HTTP fields.

⛳

Boot Validation

Service throws on startup if any credential is missing — cannot be instantiated with incomplete configuration.

🔒

Encrypted Receipt URLs

Order IDs in receipt URLs are encrypted via Laravel's Crypt — raw database IDs never exposed in browser URLs.

📋

Full Input Validation

All controller inputs validated server-side: 10-digit mobile, numeric amounts, account numbers and IFSC with regex patterns.

🗂

Pessimistic Locking

Callback handler uses LockForUpdate() — concurrent duplicate callbacks cannot both update the same transaction record.

⚡

Atomic Wallet Debits

All wallet operations run inside DB transactions with typed exception handling — partial states are impossible.

👤

ID Obfuscation

All remitter and beneficiary IDs passed via URL are encrypted/decrypted — sequential enumeration is blocked.

📄

Idempotent Fee Guard

Registration fee checked before every debit attempt — a dedicated DB flag prevents it from being charged more than once per remitter.

Development Journey

How the feature was shipped

Phase 1

Gateway research & database design

Studied the IMPS gateway API documentation, mapped out all three customer KYC states, and designed four database tables with full audit-trail columns. Defined repository interfaces before writing any concrete code.

Phase 2

Core gateway client service

Built the low-level gateway client with AES header construction, per-environment URL resolution, startup configuration validation, and all gateway operations: get-customer, register-customer, send-OTP, add-beneficiary, penny-drop, money-transfer, and status-check.

Phase 3

Onboarding orchestration service

Wrapped the base gateway client with a full onboarding flow orchestrator — automatic KYC-state detection, cache-backed state management for session continuity, and standardised flow-response formatting with explicit next-action directives.

Phase 4

Controllers, repositories & routing

Wired up all three controllers with full dependency injection, applied service subscription middleware, and defined 15+ named routes across remitter registration, beneficiary management, transfer, and callback handling.

Phase 5

Commission engine integration

Integrated the commission calculator for DMT rate lookups, wiring up the three-tier commission splits (agent / RM / SM / platform) into the order transaction model with full per-column breakdown for reporting.

Phase 6

Frontend views & registration fee migration

Built five Blade views covering the complete user journey. Added a follow-up migration to track registration fee state on existing remitter records, and refined the fee-guard logic to be fully idempotent across OTP retries and callback replays.
